# WareFlow 答辩演示手册

建议主展示 8 分钟，异常演示 2 分钟，问答备用 5 分钟。演示前先由小组成员亲自跑一遍，并能解释自己负责的模块。

## 演示准备

1. 双击启动系统.cmd，打开 http://localhost:3210，用 admin / WareFlow2026! 登录。
2. 检查“事件追踪”的自动消费开启；如果曾进行故障演练，恢复并消费待投递事件。
3. 在“一致性验证”运行完整校验，确认无差异。
4. 保留终端可用于运行 `npm test`；报告、UML 与测试 JSON 可直接从仓库打开。

## 异常演示一 整单回滚

创建包含“有机燕麦奶 1 箱”和“智能温湿度计 9999 台”的订单。记录当前库存，再点击分配。系统提示库存不足；订单仍待分配，前一商品也不留下预留。运行一致性验证，说明事务的意义。

## 异常演示二 事件故障恢复

1. 事件追踪点击“暂停自动消费”。
2. 创建一笔新订单，回到事件追踪，看到 OrderCreated 待投递。
3. 点击“模拟消费故障”，观察 RETRY 与尝试次数。页面手动演练跳过退避等待，定时消费者遵守真实 available_at。
4. 如需演示死信，累计失败五次，找到 DEAD 事件并重放。
5. 点击“消费待投递事件”或恢复自动消费，观察 DONE。
6. 再次运行一致性验证。

更强的演示是在暂停消费时完成一笔出库：订单已经 SHIPPED，运单尚未产生；恢复后运单出现。说明库存是强一致核心，物流是最终一致投影。勿将运单延迟误认为重复出库的理由。

## 常见问题与回答要点

**为什么叫事件驱动，数据库里一张表算不算？** 事件驱动取决于协同模块是否由事件触发。本系统出库事务保存 OrderShipped，后续消费者读事件并创建运单；没有同步调用运单创建。Outbox 是持久化事件投递方式，本次没有使用外部消息队列。

**如果先扣库存，事件没发出去怎么办？** 库存、流水和 Outbox 在同一个数据库事务中提交，失败一起回滚。提交后消费者可在重启后读到未处理事件。

**会不会重复扣库存或生成运单？** 命令由幂等键防重，出库只能从 PICKED 执行；消费者不扣库存，运单有唯一 order_id，副作用与消费确认同事务。对真实第三方 HTTP 仍要依赖对方幂等协议与对账，不能靠本库事务实现跨系统 exactly-once。

**库存可用量怎么算？** 账面可用等于在库减预留，FEFO 还要排除当日到期与已过期批次。预留不减少实物，出库同时减少在库与预留，取消只释放预留。

**如何防止并发超卖？** SQLite 的 BEGIN IMMEDIATE、MySQL 的全局锁行和应用 Promise 队列序列化写事务；UPDATE 还检查可用量。正确性容易验证，但全局锁限制吞吐，扩大规模需按仓或商品分片。

**为什么 SQLite 与 MySQL 都提供？** MySQL 符合标准部署方向；SQLite 减少答辩电脑环境依赖。业务测试在两种数据库运行，不能把两种数据库说成同时写入或实时复制。

**21.13% 是怎么得到的？** 1000 组固定种子任务，统一起终点与曼哈顿距离，基线按货位编号行走，优化按最近邻加2-opt。总步长从58096到45820。它是模拟网格结果，不代表真实时间、成本或碳排放收益。

**哈希链就能防所有篡改吗？** 只能检测内容与摘要不匹配；没有外部可信锚点，数据库完全控制者可以重算链，因此没有绝对不可篡改保证。

**真实设备接入了吗？** 尚未接入。温度和物流都是本地软件模拟，部署图虚线说明可能扩展；真实系统需要独立设备身份、签名和重放保护。

**AI 做了什么，组员做了什么？** 如实说明基线由 Codex 辅助实现并执行工具验证；再由每位成员陈述真实阅读、修改、测试与提交。尚未完成的人工审查不能声称已经完成。
